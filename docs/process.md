# Как мы работаем

Короткий инженерный регламент. Правила взяты из практики больших технологических компаний и урезаны до команды из пяти студентов без бюджета. Всё ниже работает на бесплатном GitHub и Jira.

## 1. Сначала пишем, потом кодим

- **Задача больше 3 поинтов** → одностраничный дизайн-документ по [шаблону](design/TEMPLATE.md) до кода. Без раздела «Как проверим» документ не утверждается.
- **Решение меняет архитектуру, контракт или модель** → ADR в [`docs/adr/`](adr/) в том же PR.
- **Встречи заменяем текстом.** К пятнице DM пишет [статус недели](status/TEMPLATE.md) (первый — [неделя 1](status/2026-w46.md)), все читают до демо. Созвон — только на демо и разбор блокеров, до 30 минут.

## 2. Код попадает в `main` только через PR

- **Работа короткими ветками:** `feat/SCRUM-31-pose`, живут не дольше 2–3 дней.
- **PR маленький:** до ~300 строк. Большую задачу режем на несколько PR за флагами или в выключенных модулях.
- **Ревью — в течение 24 часов.** Ревьюера GitHub назначает сам по [`CODEOWNERS`](../.github/CODEOWNERS): его пересобирает бот, когда кто-то захватывает роль.
- **Ключ задачи обязателен:** workflow `pr-hygiene` не пропустит PR без `SCRUM-123` в ветке или заголовке и предупредит о PR больше 400 строк.
- **ИИ-ревью перед ревью человека:** `python scripts/ai_review_prompt.py` собирает изменения и правила проекта в `ai-review.md` — вставьте его в любой ИИ-чат, замечания учтите или ответьте в PR.
- **Сообщение коммита** — по-русски, в повелительном наклонении («Добавить трекинг ByteTrack»). Закрывающий коммит задачи содержит `Task-Done: SCRUM-123`.

## 3. Защита ветки `main` — настроить один раз после публикации

GitHub → Settings → Rules → Rulesets → New ruleset → **Import a ruleset**: сейчас файл [`.github/rulesets/main-stage1.json`](../.github/rulesets/main-stage1.json), после разбора ролей — [`main-stage2.json`](../.github/rulesets/main-stage2.json) (задача SCRUM-90). Вручную то же самое, цель — `main`:

- Require a pull request before merging, 1 approval, Require review from Code Owners.
- Require status checks to pass: `test` (workflow `ci`).
- Block force pushes.

Бот ролей коммитит `ROLES.md` и `CODEOWNERS` прямо в `main`. С включёнными правилами ему нужно право обхода. Варианты:

1. Владелец репозитория создаёт fine-grained токен (Contents: read and write, только этот репозиторий) и кладёт его в секрет `ROLES_BOT_TOKEN`. Себя (Repository admin) добавляет в Bypass list правила.
2. Не включать «Require a pull request» до тех пор, пока все пять ролей не будут разобраны.

Проверьте после настройки: закройте тестовую задачу и посмотрите, обновился ли `ROLES.md`.

## 4. Качество проверяет машина

На каждом PR CI запускает:

- `ruff` и `pytest`;
- **прогон «падение → оповещение» по записи** ([`src/replay.py`](../src/replay.py)) — вся логика событий и текста без камеры и телефонов;
- **гейт качества** [`scripts/eval_gate.py`](../scripts/eval_gate.py) по всем записям в `eval/recordings`. Он сравнивает полноту, число ложных тревог и задержку с [`eval/baseline.json`](../eval/baseline.json). PR, который ухудшает метрики или выводит задержку за 4 с, не сливается.

Базу можно поднять командой `python scripts/eval_gate.py --update-baseline` — только в отдельном PR с объяснением, почему старая база устарела.

Сейчас в `eval/recordings` лежат **синтетические** записи (`"synthetic": true`). Задача ML и IoT до 24.11 (SCRUM-87) — заменить их реальными. Нужен один формат JSONL для всего прогона: видео → поза → классификатор и IMU с телефона.

## 5. Дисциплина ML

- Эксперименты логируем в MLflow локально: `pip install -r requirements-dev.txt`, затем `python scripts/log_experiment.py --name "порог 0.65" --param threshold=0.65` и `mlflow ui`. В PR указываем ID запуска.
- Тестовый набор фиксирован. На тесте не обучаемся и не подбираем пороги.
- На каждую модель, которая попала в систему, — [карточка](model-cards/TEMPLATE.md): данные, качество, где ошибается. Первая — [движок событий v0](model-cards/fall-engine-v0.md).

## 6. Цели и метрики

- **OKR до 12.12** — в [`okr.md`](okr.md). Ключевые результаты измеримы и проверяются гейтом или прогоном.
- **Метрики команды:** workflow `team-metrics` каждую пятницу считает слитые PR, медиану времени до слияния, размер PR и долю упавших запусков CI. Цели: меньше 24 часов и меньше 300 строк. Цифры идут в статус недели. Это метрики процесса, а не оценка людей.

## 7. Сбои разбираем, а не наказываем

Упал прогон, провалилось демо, потеряли данные → в течение 48 часов [постмортем](postmortems/TEMPLATE.md) без поиска виноватых. Каждое действие из постмортема становится задачей в Jira.

## 8. Релизы

- Релиз — это тег: `git tag v0.1-mvp && git push origin v0.1-mvp`. Workflow `release` прогоняет тесты и гейт, затем собирает заметки к релизу из названий PR.
- Плановые теги: `v0.1-mvp` — 01.12.2026, `v1.0-demo` — 11.12.2026.

## 9. Демо без сюрпризов

- До 05.12 — пре-мортем (SCRUM-88): «12.12 демо провалилось. Почему?» Черновик причин — [`premortem-demo.md`](premortem-demo.md). Каждую причину превращаем в задачу.
- Запасной режим: если Wi-Fi или телефон откажут, запускаем запись.

  ```bash
  python -m src.replay eval/recordings/fall_with_imu.jsonl --realtime --mqtt <ip ноутбука>
  ```

  Текст появится, ESP32 мигнёт. Запасной режим репетируем так же, как основной.
